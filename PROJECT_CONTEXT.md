Впервые исследован настоящий `data/VID_20261117_101549.mp4` (78 843 273 байта,
H.264, 922 кадра). Контейнер 30,892333 с, поток 30,818233 с со стартом
0,0741 с; 29,91735 FPS. Coded 1920×1080, rotation −90°, display 1080×1920.
PyAV теперь поворачивает пиксели один раз, PTS/time_base не изменяет.
Минимальная поддержанная версия PyAV — 19 (проверена 19.0.2, lock прежний).
Задание: docs/vision/task_v0_4_2.md. FW/оригиналы не изменялись,
COM/физический стенд агент не запускал.

Legacy-отказ OFF воспроизведён до изменения кода: кадры 13/28/43,
changed_fraction 0,0244005755 / 0,0354152281 / 0,0200121064. 100% изменённых
пикселей возле контрастных границ; marker RMSE≈1,5–1,7 ref px, локальный
optical flow median≈1,95/2,39/1,73 ref px. Gain близки к 1, offsets малы,
сильный blur не подтверждён. Сглаженный residual>40 — 0,1125/0,6151/0,0824%.
Главная причина — чувствительность прямой разности к нейтральным краевым
остаткам геометрии/ресэмплинга при движении телефона, не доказанное свечение.
Отдельные вклады интерполяции, линзы и неплоскостности не разделены.
Первый legacy-кадр 0 имел покрытие LED49=0; номер кадра не исключается
принудительно, новая регистрация проверяется по реальному покрытию.

OFF: до 24 кандидатов по всему интервалу, удерживается ≤5 лучших по
покрытию/геометрии/резкости; минимум 3 и ≥80% наблюдений на пиксель.
Сохранены >40 и >2%, но отдельно проверяются стабильные области без
контрастных краёв и низкочастотный residual; независимый абсолютный
хроматический gate не даёт принять постоянное/появившееся RGB-свечение.
При обнаруженном загрязнении выбранный интервал отвергается целиком.
Сильный blur/плохие ArUco/недостаточное покрытие также блокируют модель.
Новые OffBuildError и off_diagnostics сохраняют причины и карты при ошибке.

Промежуточный np.nanmedian тратил около 72,70 с: миллионы all-NaN предупреждений
для недостоверных пикселей. masked uint16 rank median без NaN — **9,12 с**,
изображение/маска побитно совпали. Native GUI + экспорт/профайлер около 13 с,
Qt продолжал отвечать. Покрытие: общая геометрическая маска 35,2230% кадра
эталона, оценённый dark PCB contour **73,2088%**, ROI LED49 **94,2396%**.
После исключения ArUco/quiet zones DISCOVER недоступно 28,9857% PCB.
Контур оценён алгоритмом; это не полное покрытие всей платы/неизвестных LED.

Полные C_HYBRID проходы всех 922 кадров, i9-9900K/64 GB:
KNOWN mean/P95/P99/max = 47,002/74,943/79,550/81,600 ms, wall=21,263 FPS,
910 registered / 12 invalid; DISCOVER без координат LED =
77,865/95,605/100,785/131,252 ms, wall=12,836 FPS, 911/11.
Причина invalid — Insufficient robust inlier support, декодер ничего не
пропускал. CPU ПК≈21,94/15,85%, peak sampled RSS≈340,9/356,1 MiB.
Есть отдельные 120-кадровые прогоны. Реальные 30 FPS **не достигнуты**.
Ранее синтетика использовала меньшую reference grid 1200×700; здесь 4000×2256.

C подтверждает RGB на кадрах 150/400/650. Blind DISCOVER даёт кандидатов
возле LED49, но также 68 других неизвестных кандидатов — без автоматических ID.
B проверен на 11 выбранных кадрах: RED/GREEN подтверждены; BLUE на 650
UNCERTAIN из-за отсутствия ROI в геометрической маске, полное согласие
архитектур не заявляется. KNOWN: 133 RED, 142 GREEN, 131 BLUE; 485 UNCERTAIN,

## Актуально: RGB Vision v0.4.1 — 17 ноября 2026

Добавлена девятая вкладка **«Видеоэксперимент»** в прежний GS75 RGB Vision.
Задание: docs/vision/task_v0_4_1.md. Прошивка STM32 **не менялась**,
агент настоящие порты не открывал и плату не включал.

Новые сведения оператора: FW **0.1.2 PHOTO аппаратно проверена**; LED49 RED
KP14→32 — 1035 мкА, проверен до 10000 мс; BLUE KP14→34 — 797 мкА на 1000 мс;
GREEN KP14→33 визуально подтверждён (раньше около 886 мкА). Новые сырые
журналы/точные длительности GREEN не предоставлены. Это уточняет старые
фразы ниже, но не подтверждает аппаратную приёмку нового GUI или всей платы.

Start_RGB_Vision.bat → вкладка → обнаруженный COM/COM19 → Подключить.
Диагностика требует 0.1.2 + PHOTO_LED49, DISARMED, EN0/0, FAULT NONE,
ADC VALID1/HAS_SAMPLE1/AGE≤5/ERRORS0/OVR0, SELFTEST PASS. Подключение и
диагностика не отправляют ARM/PHOTO. Запуск — повторная проверка и диалог:
видеозапись начата, U13 OPEN, R1=2700, исследуемая RGB-плата, доступ к питанию,
оператор присутствует. ПО не выдаёт эти декларации за физическое измерение.

LED49_RGB_VIDEO_TEST: OFF5000 → RED5000 → OFF3000 → GREEN5000 → OFF3000 →
BLUE5000 → OFF5000, план **31000 мс плюс обмен**. PHOTO 100…10000 мс,
OFF 100…60000 мс. Перед каждым цветом один ARM ceil(ms/1000)+5 с, один PHOTO,
соответствующий ACK/DONE ID, затем OFF/STATUS EN0. Нет PAIR-эмуляции,
повтора PHOTO, восстановления ARM_EXPIRED/FAULT или CLEARFAULT.
Пределы 2000 мкА/5 мс сохранены. AVG<100 мкА останавливает; отклонение >35%
от исторических токов предупреждает при соблюдении жёстких пределов.
MCU elapsed проверяется с допуском +0…10 мс.

COM принадлежит одному ExperimentWorker QThread. Общие preflight/PHOTO
проверки — tools/photo_led49.py, транспорт/парсер — rgb_probe.py. CLI сохранён;
CURRENT/ADCSTATUS теперь ожидаются с timeout и во время PHOTO. OFF использует
threading.Event, не ждёт DONE; чтения ≤20 мс. Закрытие пытается OFF/STATUS,
ждёт worker и закрывает порт. При USB-потере состояние выходов неизвестно.
**IWDG выключен**, физическое снятие питания должно быть доступно.

Каждый запуск — новая UUID-папка results/video_experiments/: session.json,
events.jsonl, measurements.csv, report.md. UTC + monotonic_ns, plan/actual
раздельно; ACK/DONE raw+timestamps, токи/выборки/ELAPSED_MS/причина/FAULT.
Аварийные журналы сохраняются, завершённые последующей диагностикой не меняются.
Каталог исключён из Git; исходные результаты, медиа и карта не перезаписывались.
Модули разделены: software/hardware/{scenario,experiment,journal,video_link,
simulator}.py; software/gui/{experiment_pane,experiment_worker}.py.

MP4/MOV привязывается без копирования; metadata читаются через PyAV в worker:
размер/mtime, разрешение/FPS/длительность, PTS/time_base, доступные теги.
Hash большого файла пропущен с причиной. Поздняя замена — video_history.
Есть прежний просмотр и передача пути в Benchmark. Для стендового сценария
проект/карта не нужны; для Benchmark нужны. Синхронизация UNALIGNED,
offset/uncertainty=null; optical_transitions и RGB anchors подготовлены.
UTC телефона/ПК и TX USB не считаются фронтами света. Добавлен pyserial 3.5.

Инструкция и первое испытание: docs/vision/video_experiment.md. Скриншот native
Windows Qt: docs/vision/screenshots/v041_video_experiment.png. Полный пример
**имитатора**, с ускоренным виртуальным временем: docs/vision/examples/v041_simulated/.

Финальная проверка: **104 Python-теста PASS (81,145 с)**, включая 13 тестов
исполнителя с подслучаями отказов и 8 Qt offscreen-тестов новой вкладки;
**2 C-регрессии PASS**. Native Qt backend=windows, снимок проверен визуально.
Все 341 исходных файла из firmware/data/RGB_Vision/results/docs/images и
локальная карта совпали с контрольными суммами перед работой. Подробности:
docs/vision/v041_validation.md; полные локальные логи build/vision_v041/.

Следующий этап выполняет оператор: PHOTO=1000 мс, отдельный тест красной OFF
во время RED, затем штатный 31-секундный сценарий с Redmi Note 11 Pro
1080p/30, импорт MP4 и Benchmark. Новую GUI-приёмку нельзя объявлять успешной

## Актуально: RGB Vision v0.4-perf

Добавлена восьмая вкладка «Производительность видео» в существующее GUI.
Исходное задание: docs/vision/task_v0_4_perf.md. Пользователь явно подтвердил,
что реального видео пока нет. Замеры выполнены на синтетических MP4 с
OFF→RGB, движением камеры и двумя кадрами потери ArUco; реальные OFF/R/G/B
проверены как фото-регрессия. Прошивка и исходные данные сохранены.

Профилирование perf_counter_ns: decode, ArUco, homography, rectification,
background compensation, LED detection, color, events, total. Стадии
exclusive, сохраняются Mean/P50/P95/P99/max, отдельные decode/compute/wall FPS,
CPU, sampled RSS, registered/invalid/lost, бюджеты 10/15/25/30/60 с расчётной
очередью. PNG/GUI/отчёты вынесены из горячего цикла. PyAV 19.0.2 даёт
PTS/time_base и VFR; requirements и lock обновлены.

Автоматический OFF: минимум три независимо зарегистрированных наблюдения,
удерживается ≤5 кадров, медиана по 64-строчным плиткам и маска ≥80%/≥3
наблюдений. Отказы по геометрии, свету/объектам и возможному свечению.
На штатном fixture принято 4 кадра, маска 74,6489%. Интервал должен быть
гарантированно OFF оператором; метод не доказывает электрическое отключение.
Обновление требует явного гарантированного OFF, при последнем ON запрещено.

Сравнены A_BASELINE (старый алгоритм), A_CACHED, B_CACHED_FULL без диагностик,
C_HYBRID (уменьшенный ArUco, исходные углы, новый H, coarse-фон и full-res ROI).
При плохой геометрии ROI — полный ArUco fallback (потребовался на реальном
BLUE). Потеря ArUco не создаёт новые LED ID, временное событие прерывается.

ПК: i9-9900K, 64 GB, Python 3.12.3, OpenCV 4.14.0/16 threads, Windows 10.
Synthetic reference 1200×700; входы 1080p/1440p/4K, по 120 кадров/4 с.
C KNOWN mean=21,628/23,321/30,057 ms; P95=25,327/27,236/32,398 ms.
4K worst=108,431 ms, mean>25 — запаса для устойчивых 30 нет.
DISCOVER 1080p mean=58,353, P95=64,854 ms: 30 FPS не достигаются.
Открытый Windows GUI: C 1080p mean=21,127 ms, без изменений качества.
Все варианты: 118 зарегистрированных, 2 намеренно invalid, пропусков 0,
RGB без ошибок; centroid delta<0,025 px, local geometry delta<0,007 px.

Полный прогон: 83 Python-теста и две C-регрессии прошли. Исправлен тестовый
wait_idle: QTest.qWait удерживал GIL и тормозил Python-worker; теперь ожидание
передаёт GIL, как штатный QApplication.exec. Native GUI-замеры от этого
не зависели. Видеоспецифические intrinsics пока не поддержаны
(benchmark требует camera_model=null), старый фотоанализ их сохраняет.

Отчёт: docs/vision/perf_v04/report.md, summary.json и CSV/PNG рядом;
инструкция: docs/vision/video_performance.md. Полные локальные benchmark
JSON/OFF/видео — build/vision_v04/final_*/ и GUI-каталог из latest_gui.txt.
Рекомендация: C для известных LED, B для контроля качества/DISCOVER.
Следующий этап — реальные длинные видео с реальной картой 4000×2256,
маленькими ArUco и VFR. Устойчивые 30 FPS на них **не подтверждены**.

## Актуально: RGB Vision v0.3

Разработано единое **GS75 RGB Vision**. Запуск `Start_RGB_Vision.bat` через
pythonw без постоянного терминала. Семь вкладок: проект, калибровка, фото,
видео, результаты, настройки, журнал. Прошивка в этом этапе **не менялась**.
Оператор сообщил, что реальные RGB-фото получены при испытании FW 0.1.2.
Точные длительности/CDC-протоколы этих опытов не предоставлены; не приписывать
им ранее записанные токи или результаты иных опытов. Утверждения ниже
«GREEN/BLUE ещё нет» относятся к предшествующему этапу.

Проект исследования — отдельный `gs75_rgb_vision_project.json`: ссылки на
карту v1, эталон, фото/видео, роли, настройки, историю и отчёты. Пути
переносимые, отсутствующие файлы можно найти заново. Калибровка проверяется
по hash/версии и перед каждой парой вручную не выбирается. Редактор LED49,
названия клавиш, Undo/Redo и autosave сохранены.

Фото: мультиимпорт, миниатюры, Drag & Drop, явные OFF/ON/REFERENCE, фоновый
последовательный batch с прогрессом/отменой, UUID-отчёты JSON/CSV/PNG.
История открывается повторно; есть переименование, экспорт, повтор,
сравнение запусков, связанный выбор в таблице/изображении. KNOWN показывает
ON/OFF/UNCERTAIN; DISCOVER требует ручного PCB ID и предотвращает дубликаты.

Видео: MP4/MOV/AVI при наличии декодера, Play/Pause, seek, выбор кадров
как OFF/ON и автоматическое сохранение выбранных PNG для истории. Весь файл
не копируется и не загружается в память. Timestamp декодера отделён от
оценки по FPS. ArUco определяется заново для каждого выбранного кадра.
Полного видеоанализа, камеры и синхронизации STM32 ещё нет.

Реальная приёмка **через новое GUI**: LED49 RED/GREEN/BLUE; OFF/OFF — OFF;
других ошибочно идентифицированных включённых LED нет. Причина BLUE→MIXED:
v0.2 голосовала по ON-цвету, включая фон/отклик камеры. v0.3 использует
компенсированный прирост и отношение второго компонента к первому:
≤0,45 один цвет, ≥0,70 MIXED, между ними UNCERTAIN. Для BLUE ratio=0,241862,
confidence=0,758138 (эвристика, не вероятность).

Документация: docs/vision/gui_guide.md, video_import.md, gui_architecture.md,
v03_validation.md. Скриншоты — docs/vision/screenshots/v03_*.png.
Проверены Qt offscreen, настоящий backend Windows, BAT/pythonw, тестовый MP4
(кадр 6, 600 мс) и анализ выбранных кадров. Фото, карта и hardware-результаты
не перезаписаны. Отчёты локальны: build/vision_v03/gui_acceptance_*/.

## 2. Электрическая архитектура стенда

- MCU: **STM32F411RET6**, кварц HSE 8 МГц, SYSCLK 96 МГц, USB FS 48 МГц.
- FPC: сигнальные сети `KP1`…`KP40`; контакты экрана разъёма — GND. **Реальную физическую ориентацию pin 1, контактов и шлейфа перед подключением проверить мультиметром, а не угадывать по виду сверху/снизу.**
- SOURCE: U1–U5 = `74HCT4051` (выбор одной из 40 линий из положительной цепи).
- SINK: U6–U10 = `74HCT4051` (выбор одной из 40 линий в цепь измерительного шунта и GND).
- U11/U12 = `74HCT138`, выбор одного из 5 банков. `BANK_EN=LOW` блокирует соответствующую группу.
- Источник: `USB_+5V → R1=2700 Ω → SRC_BUS → SOURCE mux`.
- Возврат: `SINK mux → SINK_BUS → R2=100 Ω → GND`.
- ADC: `SINK_BUS → R3=1000 Ω → PA0`, фильтр C15=10 нФ на GND.
- Опциональная параллельная ветвь `U13 + R18=1500 Ω` **должна оставаться разомкнутой** во время первичных испытаний.
- GPIO SOURCE: PA4–PA6 (`CH0..2`), PA7–PA9 (`BANK0..2`), PA10 (`BANK_EN`).
- GPIO SINK: PC6–PC8 (`CH0..2`), PC9–PC11 (`BANK0..2`), PC12 (`BANK_EN`).
- USB D− PA11, D+ PA12, SWD PA13/PA14. USB VBUS sensing **отключён**, поскольку PA9 используется как SRC_BANK2.

Таблица выбора банков (проверена программно по EasyEDA; не заменяет прозвонку платы):

| Сети FPC | SOURCE | SINK | BANK | CH |
|---|---|---|---|---|
| KP1–KP8 | U1 | U6 | 4 | 0–7 |
| KP9–KP16 | U2 | U7 | 3 | 0–7 |
| KP17–KP24 | U3 | U8 | 2 | 0–7 |
| KP25–KP32 | U4 | U9 | 1 | 0–7 |
| KP33–KP40 | U5 | U10 | 0 | 0–7 |

Формулы: `channel=(pin-1)%8`, `bank=4-(pin-1)/8` (целочисленное деление). Имеется 40×39 = **1560 направленных пар**, пока только их программная адресация проверена полностью.

## 3. Настройки безопасности FW 0.1.1 — НЕ ослаблять

- После Reset — `DISARMED`, обе `BANK_EN=0`; автоматического включения нет.
- `ARM s`: только явное разрешение на 1–60 секунд.
- `PAIR src snk duration_ms`: разные контакты 1…40, длительность **10–300 мс**.
- `OFF` / `DISARM` должны выключать обе группы; при `FAULT` требуется устранить причину и выполнить `CLEARFAULT`, затем новый `ARM`.
- До смены адресов обе группы выключаются; после безопасных задержек включается SINK, затем SOURCE.
- `ADC_STALE_MS=5`, аварийный порог текущей конфигурации `CURRENT_LIMIT_UA=2000` (сверить точное имя определения с `firmware/App/Inc/board_config.h`).
- Предел 2 мА — программная диагностика; **физический ток в первую очередь ограничивается R1**, а программная защита не заменяет аппаратную.
- Проверка времени импульса производится из SysTick независимо от USB CDC, но это ещё не измеренная осциллографом аппаратная гарантия.
- Не вводить постоянный PAIR, автоматический перебор или увеличение тока для «улучшения видимости» без новой оценки безопасности.
- Не подключать внешний источник питания к FPC; не соединять несколько независимых источников питания без схемной проверки.

## 4. История дефекта ADC и исправление

FW 0.1.0: непрерывный ADC (~49 квыб./с) опрашивался максимум ~1 краз/с, overrun не восстанавливался. Наблюдение: `SELFTEST -> ERR ADC_INVALID`; `CURRENT -> RAW=2 ... AGE_MS=115331 VALID=0`. Фактический флаг OVR в том опыте не снимался; причина подтверждена анализом алгоритма, а не снимком регистра при отказе.

FW 0.1.1: одиночные неблокирующие преобразования примерно **1 кГц** (`CONT=0`), в том числе в DISARMED; мониторинг EOC/OVR, тайм-аут, защёлка FAULT при ошибках, `ADCSTATUS`. Подробности: `docs/adc.md`.

**Реальная проверка FW 0.1.1 на плате:**

```text
PING -> PONG
INFO -> FW: 0.1.1
STATUS -> STATE=DISARMED SRC_EN=0 SNK_EN=0 FAULT=NONE
ADCSTATUS -> STARTS=146796 SAMPLES=146796 VALID_SAMPLES=146796
             ERRORS=0 OVR_COUNT=0 TIMEOUTS=0 ... AGE_MS=0 VALID=1
CURRENT (без нагрузки) -> RAW=2 MV=2 CURRENT_UA=16 AGE_MS=0 VALID=1
SELFTEST -> SELFTEST=PASS PHYSICAL_MUX=UNTESTED
```

`CURRENT_UA=16` без нагрузки — зарегистрированный результат, **не** калиброванный ноль и **не** точность измерения.

| DONE FAULT | `NONE` | `NONE` |
| Последующий STATUS | `STATE=DISARMED`, `SRC_EN=0`, `SNK_EN=0`, `FAULT=NONE` | то же |

Оба теста выдали `PASS: OFF ended the pulse; firmware reported both BANK_EN disabled.` До импульсов `ADCSTATUS` показал `VALID=1`, `ERRORS=0`, `OVR_COUNT=0`; `SELFTEST=PASS`. Задержка передачи команды OFF после ACK измеряется на Windows и **не равна** достоверному физическому времени включения или выключения ключей. Пример: DONE принят через 15 мс (50-мс тест) и через 31 мс (100-мс тест) после отправки OFF — включает USB/host latency, а не только время ключа. Число выборок 67/115 меньше полного 300-мс импульса, что согласуется с прерыванием.

**Вывод:** команда OFF прерывает активный PAIR на контрольной нагрузке, и прошивка сообщает об отключении обеих групп; оба опыта прошли без FAULT. **Не проверены осциллографом:** реальные фронты `BANK_EN`, задержка отключения, состояние при Reset или авариях. Не писать «физически подтверждённое время отключения». После переноса результатов дополнить `docs/hardware_validation.md`, обновить README и коммитить эти изменения без вмешательства в прошивку.

## 6. Новые измерения оригинальной RGB-платы — 16.11.2026

По сообщению оператора на **отдельной плате подсветки** измерены сопротивления **между точкой/цепью, обозначенной оператором как анод, и цветовыми цепями**:

| Цепь, указанная оператором | Измеренное сопротивление |
|---|---:|
| Анод ↔ красный (R) | **100 Ом** |
| Анод ↔ синий (B) | **75 Ом** |
| Анод ↔ зелёный (G) | **16 Ом** |

**Статус:** сообщил/измерил оператор; фотография с обозначениями компонентов, схема трассировки, способ измерения (в схеме / выпаян), допуски и точная электрическая функция этих сопротивлений пока не приведены. Не утверждать без дополнительной проверки, что это независимые последовательно включённые резисторы каждого диода или что уже доказан тип общей полярности всех LED. При измерении на установленной плате возможны обходные пути через другие элементы.

**Практический вывод:** все три величины значительно меньше R1=2700 Ом стенда, поэтому на первом этапе **не менять** R1 и не замыкать U13. Сначала подтвердить по фотографиям/прозвонке реальные общие цепи и направление включения; только затем разрешать пробное питание отдельных пар. Не предполагать напряжение открытия LED и не считать отсутствие видимого свечения доказательством отсутствия электрического соединения.

Для воспроизводимости позже добавить фото обеих сторон RGB-платы, маркировку/координаты резисторов, точки измерения, режим мультиметра, факт подключения/отключения шлейфа и таблицу уточнений в `docs/hardware_validation.md`.

## 8. Как продолжить на любом компьютере с VSCode

Установить: Git, VSCode, Python 3, ARM GNU toolchain / STM32CubeCLT, CMake, Ninja, STM32CubeProgrammer. Для проверенных MSVC host-тестов на Windows также Visual Studio Build Tools с MSVC и Windows SDK (для ARM-сборки не обязательны). Убедиться в доступности инструментов через PATH.

### Если проект ещё не клонирован

```powershell
git clone https://github.com/AlexeyNV/GS75_RGB_Research.git
cd GS75_RGB_Research
code .
```

### Если репозиторий уже есть

```powershell
git status
git fetch origin
git log -5 --oneline
# Только при чистом рабочем дереве и после проверки текущей ветки:
git pull --ff-only origin main
code .
```

Не выполнять `reset --hard` и другие уничтожающие локальные изменения команды только ради синхронизации. Локальную историю и рабочие изменения надо сначала сохранить.

### Проверка инструментов и сборка

```powershell
arm-none-eabi-gcc --version
cmake --version
ninja --version
cmake -S firmware -B build/firmware -G Ninja '-DCMAKE_TOOLCHAIN_FILE=cmake/arm-gcc.cmake'
cmake --build build/firmware
python -m pip install -r tools/requirements.txt
python -m unittest discover -s tests -p 'test_*.py' -v
```

Host-тесты под установленным Visual Studio 2022:

```powershell
cmake -S tests -B build/host -G 'Visual Studio 17 2022' -A x64
cmake --build build/host --config Debug
ctest --test-dir build/host -C Debug --output-on-failure
```

На Linux/другой конфигурации использовать доступный host-компилятор/генератор и отдельный build-каталог. **`build/` не переносить:** CMake cache содержит абсолютные пути; ELF/BIN/HEX пересобираются. Библиотеки CubeF4, необходимые для данной CMake-сборки, сохранены в репозитории.

**USB DFU:** на реальной плате FW 0.1.1 успешно записывалась через встроенный USB DFU; точная операторская команда прошивки в этом журнале не зафиксирована. Не выдумывать процедуру — использовать ранее проверенную на данной плате последовательность STM32CubeProgrammer и штатный режим BOOT. Для альтернативного SWD-пути см. корневой README. После записи проверять версию `INFO`.

**USB CDC:**

```powershell
python tools/serial_console.py --port COM19
```

`COM19` — порт исходного проверенного ПК; на новом ПК найти фактический COM-порт. Начинать пассивно: `PING`, `INFO`, `STATUS`, `ADCSTATUS`, `CURRENT`, `SELFTEST`. Не отправлять `ARM`/`PAIR` с оригинальной подсветкой до выполнения проверок из раздела 7.

`.ioc` сохранён, но его открытие/полная регенерация через GUI CubeMX не были проверены. Опорный проект сборки — CMake. Регенерацию CubeMX делать в отдельной папке, не перезаписывать USB и защитную логику без сопоставления.

## 9. Как сохранять прогресс между сеансами

После **каждого** аппаратного эксперимента:

1. Добавить дату, версию FW/commit, подключение и приборы, фактические команды/ответы, измерения и пределы выводов в `docs/hardware_validation.md`.
2. Обновить разделы «подтверждено / не подтверждено», электрические гипотезы и ближайшие шаги в **этом** `PROJECT_CONTEXT.md`. Не оставлять в тексте уже опровергнутые утверждения «проверка не проводилась».
3. Если менялся код — обновить тесты, сборочные инструкции, FW-версию и журнал изменений; не писать «hardware verified» без испытаний.
4. Коммитить **оба** вида документации вместе с кодом/тестами, если они изменены; затем `git push` и убедиться, что коммит доступен на GitHub.

```powershell
git status
git add PROJECT_CONTEXT.md docs/hardware_validation.md
git commit -m "docs: record verified OFF interruption and RGB investigation plan"
git push origin main
git status
```

Команда `git add` предполагает, что в локальном репозитории эти файлы изменены. Если другие изменения уже имеются, сначала осмотреть `git diff`, не включать посторонние файлы автоматически. Не записывать в Git секреты и большие коллекции необработанных видео/снимков. Сборочный мусор исключён `.gitignore`.
