# PHOTO LED49 — FW 0.1.2

Уточнение оператора в задании v0.4.1 от 17.11.2026: FW 0.1.2 фактически
проверена на стенде. RED — 1035 мкА, до 10000 мс; BLUE — 797 мкА на 1000 мс;
GREEN визуально подтверждён, ранее около 886 мкА. Новые сырые журналы не
приложены. Ниже сохранена история v0.2/v0.3; фраза о подтверждённой только
0.1.1 относится к прежнему этапу. Новое [GUI](vision/video_experiment.md)
прошивку не меняет и само ещё требует отдельной аппаратной приёмки.

В задании RGB Vision v0.3 оператор сообщил об испытании FW 0.1.2 с получением
OFF/RED/GREEN/BLUE. Точные команды, длительности и CDC-измерения этих опытов
не предоставлены. Следующий абзац сохраняет статус разработки v0.2,
а не опровергает последующее сообщение оператора. В этапе v0.3 прошивка
не менялась; агент не прошивал плату и не управлял выходами.

Реализовано и проверено программно. **На плате по-прежнему подтверждена
только FW 0.1.1. Новая FW 0.1.2 не прошивалась агентом.**

Команда `PHOTO LED49 RED|GREEN|BLUE duration_ms` даёт одно непрерывное
включение на 100–10000 мс. Рекомендуемая длительность для фото — 5000 мс,
после постепенных первых проверок. Разрешены только SOURCE=14 и SINK=32,
33, 34 соответственно. Другие LED, произвольные контакты и сочетания цветов
отклоняются. `PAIR` сохраняет диапазон 10–300 мс.

U13 OPEN, R1=2700 Ом; эти физические условия прошивка определить не может.
Предварительно нужны свежий ADC, отсутствие FAULT, корректные GPIO и явный
`ARM`. PHOTO и PAIR используют одну машину ACTIVE, одновременно невозможны.
Повторный ARM во время ACTIVE запрещён. Автоматического повторного включения нет.

## Ответы

```text
ARM 20
OK ARM_TIMEOUT_S=20
PHOTO LED49 RED 5000
ACK ID=1 MODE=PHOTO LED=49 COLOR=RED SRC=14 SNK=32 DURATION_MS=5000
```

Затем асинхронный ответ (числа измерений здесь намеренно не подставлены):

```text
DONE ID=1 STATE=OFF CURRENT_AVG_UA=... CURRENT_MAX_UA=... SAMPLES=... FAULT=NONE REASON=TIMEOUT MODE=PHOTO LED=49 COLOR=RED ELAPSED_MS=...
```

`ELAPSED_MS` — разность MCU tick при запуске и снятии EN, с квантованием
1 мс; это не осциллографическое измерение оптического импульса. При отсутствии
ADC-выборок остаётся `MEASUREMENT=UNAVAILABLE`. Среднее/максимум/число выборок
считаются за одно непрерывное включение. DONE PAIR сохранён без изменения.
STATUS добавляет `MODE=PHOTO|PAIR|NONE`; INFO — `CAPABILITIES: PHOTO_LED49`.

## Защиты и ограничения отказоустойчивости

Срок PHOTO проверяется в SysTick независимо от CLI/TX. ARM продолжает
истекать; по его окончании PHOTO прекращается с ARM_EXPIRED. Возраст ADC
более 5 мс, invalid/overrun ADC, ток выше 2000 мкА, FAULT, USB reset/suspend/
disconnect прекращают операцию. Доставка DONE при потере USB не гарантируется.
OFF обходит очередь, выключает GPIO в RX callback и снимает ARM. FAULT
остаётся защёлкнутым; восстановления ADC/USB недостаточно для включения.

При Reset ранний Board_Init сначала сбрасывает защёлки EN, затем настраивает
GPIO; до него предназначены аппаратные подтяжки R16/R17. Состояние запуска
DISARMED. HardFault/NMI/Error_Handler выключают EN.

**IWDG не включён.** Новый аппаратный watchdog без проверки длительности
сброса, фактических EN и перехода в используемый ROM DFU нельзя считать
проверенным. В этой задаче физические испытания запрещены; оставлены прежняя
загрузка, BOOT/DFU и option bytes. Следующий отдельный этап IWDG: определить
окно по LSI, кормить только после успешного прохода main, испытать зависание
main и запрещённые IRQ, измерить EN при reset и повторно проверить DFU.
Сейчас при зависании CPU с отключёнными прерываниями SysTick не гарантирует
отключения по времени. R1 ограничивает ток; для прекращения такого опыта
оператор отключает питание. PHOTO не объявляется полностью отказоустойчивым.

## Чистая сборка и USB DFU — выполняет оператор

ARM GCC/CMake/Ninja должны быть в PATH. Для чистой сборки выбрать новый каталог:

```powershell
cmake -S firmware -B build/firmware-photo -G Ninja '-DCMAKE_TOOLCHAIN_FILE=cmake/arm-gcc.cmake'
cmake --build build/firmware-photo
```

Файлы: `build/firmware-photo/GS75_RGB_Research.elf`, `.bin`, `.hex`.
Перед прошивкой отключить RGB-нагрузку и перейти в ROM DFU ранее проверенной
на этой плате процедурой BOOT/Reset. Уточнить USB-индекс по списку:

```powershell
STM32_Programmer_CLI -l usb
STM32_Programmer_CLI -c port=USB1 -w build/firmware-photo/GS75_RGB_Research.bin 0x08000000 -v
```

`USB1` заменить на найденный порт целевой платы. Адрес проверен по linker
script; синтаксис — по локальной справке STM32CubeProgrammer. Команды записи
в этой задаче не выполнялись. После verify вернуть BOOT в рабочее положение,
выполнить Reset, проверить INFO: FW 0.1.2 и CAPABILITIES PHOTO_LED49.
Выходы должны оставаться выключенными.

## Первое аппаратное испытание

1. Без нагрузки: PING, INFO, STATUS, ADCSTATUS, CURRENT, SELFTEST. Проверить
   DISARMED, SRC_EN=SNK_EN=0, FAULT=NONE, VALID=1, AGE_MS≤5, рост SAMPLES.
2. При снятом питании подготовить подтверждённую LED49, U13 OPEN, R1=2700 Ом.
   Проверить соединения и отсутствие постороннего питания.
3. Выполнять каждый блок отдельно, ждать DONE, проверять ток и STATUS.
   Переходить к следующей длительности только после успешной предыдущей.

```text
ARM 20
PHOTO LED49 RED 100
# дождаться DONE, проверить ток/FAULT/REASON
OFF
STATUS

ARM 20
PHOTO LED49 RED 1000
# дождаться DONE
OFF
STATUS

ARM 20
PHOTO LED49 RED 5000
# дождаться DONE
OFF
STATUS

ARM 20
PHOTO LED49 RED 10000
# дождаться DONE
OFF
STATUS
```

Строки с `#` — пояснения, не команды CDC. Для GREEN/BLUE аналогично, начиная
со 100 мс. Не расширять проверенную распиновку по одному току.
Отдельно прервать PHOTO командой OFF, проверить DONE REASON=OFF и EN=0;
проверить ARM 1 + PHOTO 5000 (ARM_EXPIRED) и USB suspend. Физические фронты
EN/Reset и время отключения измерить прибором. При отклонении тока, FAULT,
отсутствии DONE или выключения прекратить опыт; повторный ARM автоматически
не выполнять. Сохранить фактические результаты в docs/hardware_validation.md.

## Python

```powershell
.\.venv\Scripts\python.exe tools/photo_led49.py --port COM19 --color red --duration-s 5
```

Скрипт запросит ввод PHOTO. Для заранее осознанного подтверждения есть
`--confirm-photo`. Проверки PING/INFO/STATUS/ADCSTATUS/SELFTEST идут до ARM;
версия поддерживается строго 0.1.2 с нужной capability. Один ARM с запасом
5 с, один PHOTO, сопоставление ID ACK/DONE, контроль CURRENT, затем OFF.
Ошибка/Ctrl+C также инициирует OFF; если USB потерян, скрипт явно сообщает,
что подтверждения нет. Продление ARM и fallback на серию PAIR отсутствуют.
Журнал TX/RX/ошибок с UTC и monotonic time: новый `results/photo_led49_*.jsonl`
или `--log путь`. Существующий файл не перезаписывается.

Найденный исходный tools/photo_led49.py имел размер 0 байт: прежний запуск
этого конкретного файла не отправлял бы никаких команд. Исходника и TX/RX
неудачной предыдущей попытки нет, поэтому её историческую причину установить
нельзя. Реальный протокол проверен по cli.c: PING → PONG, INFO многострочный
до END INFO; ARM → OK, запуск → ACK ID, завершение → DONE ID.
