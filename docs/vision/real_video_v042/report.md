# Реальное видео GS75 — v0.4.2

Исходный MP4: data/VID_20261117_101549.mp4, 78 843 273 байта, H.264, 922 кадра.
Контейнер 30.892333 с; поток 30.818233 с, старт PTS 0.074100 с; 29.91735 FPS.
Coded 1920×1080; display rotation −90° (по часовой стрелке), результат 1080×1920.
PTS/time_base сохранены; поворот выполнен один раз. Нет скрытого пропуска кадров.
Оригиналы и FW не менялись; COM/стенд агент не запускал. Исходные медиа/диагностические фото в Git не включаются.

## Первопричина

Legacy-ошибка воспроизведена на исходном коде до изменений с теми же кадрами и долями.

| Кадр | Raw >40, % | Изменившиеся пиксели возле контрастных границ, % | Median/P95 local displacement, reference px |
|---|---:|---:|---:|
| 13 | 2.440058 | 100.0 | 1.951 / 3.715 |
| 28 | 3.541523 | 100.0 | 2.389 / 6.362 |
| 43 | 2.001211 | 100.0 | 1.730 / 3.281 |

При RMSE ArUco около 1,5–1,7 reference px остаются небольшие локальные смещения белой шелкографии.
Они дают большие перепады яркости на узких краях, а legacy считает их по всей общей области и сравнивает с жёсткими 2%.
Нейтральные высококонтрастные остатки принимались за освещение/движущийся объект. После небольшого пространственного сглаживания
доли >40 для кадров 13/28/43: 0,1125% / 0,6151% / 0,0824%. Gain близки к 1, offsets малы; сильного motion blur не видно
по Laplacian variance (примерно 287–302), больших цветных областей в этих OFF-кадрах нет.
Масочная граница объясняет только около 5–7% изменившихся пикселей, поэтому это не преимущественно край valid_mask.
Телефон двигался; независимый optical flow подтверждает остатки совмещения. Отдельные вклады интерполяции warp, точности углов,
линзы/неплоскостности и движения без дополнительной калибровки не разделены — их нельзя объявить отдельно доказанными.
Первый legacy-кадр 0 имел покрытие LED49=0; он был плохой единственной опорой и не мог считаться достаточным для модели.
Поддержка RANSAC может меняться; новая версия проверяет фактическое покрытие каждого кандидата, а не исключает номер 0 принудительно.

## Исправление

До 24 кандидатов в интервале, удерживаются максимум 5 лучших полноразмерных наблюдений. Выбор — покрытие/геометрия/резкость,
а не первые три кадра. Интервал просматривается до конца: найденное свечение/перекрытие/существенная смена света не маскируются
ранее накопленными хорошими кадрами. Отдельные gates: абсолютное локальное цветное свечение; affine lighting; raw residual
в стабильных областях без контрастных краёв; низкочастотный residual; ArUco/blur/ROI coverage. Пределы >40 и >2% не повышались.
Медиана учитывает только достоверные наблюдения, valid требует ≥3 и ≥80% кадров. Точная целочисленная медиана исключает
миллионы all-NaN предупреждений NumPy: 72,699 → 9,120 с без экспорта картинок, изображение и маска побитно совпали.
Native GUI с экспортом диагностики и профайлером завершил построение примерно за 13 с; Qt продолжал отвечать.

## Производительность

ПК: i9-9900K, 64 GB, Python 3.12.3, OpenCV 4.14.0, PyAV 19.0.2. Reference grid 4000×2256.

отдельным проходом; измеренный проход всегда стартует с кадра 0. DISCOVER получил пустой список LED координат.

Все invalid вызваны Insufficient robust inlier support; пропусков декодирования 0. RSS — sampled process peak, не размер одного алгоритма.
KNOWN и DISCOVER имеют разные fallback/локальные проверки, поэтому число зарегистрированных кадров может различаться.
30 FPS не достигнуты ни в одном полном режиме; источник работал примерно на 29,92 FPS. Одного среднего недостаточно для realtime.
Предыдущая синтетика 1080p: C KNOWN mean=21,628/P95=25,327 мс; C DISCOVER mean=58,353/P95=64,854 мс.
Настоящий KNOWN примерно в 2,17 раза медленнее по mean, DISCOVER в 1,33 раза; сравнение не является чистым speedup:
другая reference grid (1200×700 раньше), реальные мелкие ArUco, насыщенная текстура/сжатие, поворот, fallback и условия CPU.
Медленный B_CACHED_FULL проверен на 11 выбранных кадрах для каждого режима, примерно 1,8–1,9 с compute/frame.
Декодирование этого поднабора вне timed section, поэтому его FPS нельзя непосредственно сравнивать с полными C.
Один C вариант не является независимой проверкой самого себя: quality=UNCOMPARED_SINGLE_VARIANT.

## RGB и временные границы

В настоящем GUI выполнены build OFF, KNOWN/DISCOVER по 120 кадров и экспорт. Полные 922-кадровые замеры — через общий benchmark API без GUI.
На кадрах 150/400/650 C подтверждает LED49 RED/GREEN/BLUE. DISCOVER без координат даёт соответствующие оптические кандидаты возле LED49.
Полноразмерный контроль B подтверждает RED/GREEN; BLUE на кадре 650 у B остаётся UNCERTAIN из-за нулевого геометрического покрытия,
поэтому согласие всех архитектур не заявляется. C использует более удачную геометрию; дополнительное визуальное подтверждение доступно в кадрах.
Кроме кандидатов рядом с LED49, DISCOVER дал 68 других неидентифицированных кандидатов. Они не объявлены другими LED и не получают PCB ID.
KNOWN: 133 RED, 142 GREEN, 131 BLUE; 485 UNCERTAIN, 19 OFF, 12 неанализируемых кадров. Нет других известных LED ID.
UNCERTAIN на OFF часто вызван ахроматическими остатками белой шелкографии, а не доказанным свечением. Это открытое ограничение детектора.
Предварительные EventAggregator-события сохранены в полном JSON; они фрагментированы. Геометрические отказы не склеиваются и не подтверждаются.

Это границы между соседними видеонаблюдениями цветного сигнала (примерно 33–34 мс), а не точные электрические фронты.
Экспозиция, rolling shutter, USB и неизвестная связь с CDC оставляют дополнительную неопределённость. Плановые времена не использовались
для принятия OFF или выставления этих границ. Синхронизация со STM32 остаётся UNALIGNED.
