Ты — инженер-разработчик алгоритмов компьютерного зрения, OpenCV, Python и PySide6.

https://github.com/AlexeyNV/GS75_RGB_Research

Актуальный модуль производительности: v0.4-perf, коммит `e2ff615`.

## Главная задача

Впервые получено **реальное видео RGB-платы MSI GS75**, записанное во время автоматического эксперимента с последовательным включением LED49 RED/GREEN/BLUE.

При запуске Benchmark приложение не может автоматически сформировать OFF-модель, хотя первые кадры видеозаписи содержат выключенную подсветку.

Необходимо:

1. Самостоятельно открыть реальное видео.
2. Воспроизвести ошибку.
3. Исследовать конкретные отклонённые кадры.
4. Установить причину ошибочной отбраковки.
5. Исправить алгоритм построения Automatic OFF, сохраняя проверки безопасности и качества.
6. Повторить анализ на реальном видео.
7. Измерить производительность KNOWN_LEDS и DISCOVER.
8. Обеспечить удобную диагностику и корректные сообщения в GUI.

**Не решать проблему простым увеличением порога `changed_fraction`.**

## 1. Исходные данные

Реальный файл находится в рабочем каталоге проекта:

```text
data/VID_20261117_101549.mp4
```

Также имеются:

```text

data/reference/gs75_rgb_off.jpg
data/off.jpg
data/red.jpg
data/green.jpg
data/blue.jpg
```

Все исходные файлы должны оставаться неизменёнными.

Параметры настоящего MP4, независимо проверенные перед постановкой задачи:

- Продолжительность: 30,892 с.
- Видеокадров: 922.
- Средняя частота: примерно 29,92 FPS.
- Кодек: H.264.
- Исходная видеоматрица: 1920×1080.
- Метаданные ориентации: поворот −90°, отображение вертикальное 1080×1920.
- Размер файла: приблизительно 79 МБ.

В видеозаписи последовательно наблюдаются:

OFF → RED → OFF → GREEN → OFF → BLUE → OFF.

Начальные секунды действительно содержат выключенную подсветку.

При предварительном просмотре красное свечение становится заметным ориентировочно после 3 секунд. Точные времена переходов необходимо измерить по видео самостоятельно. Не считать плановые времена сценария точными оптическими временными метками.

Если видео отсутствует в рабочей среде агента, сообщить об этом. Не подменять его синтетическим роликом и не утверждать, что реальное испытание выполнено.

## 4. Диагностика конкретных кадров

Для кадров 0, 13, 28, 43 и дополнительных кадров начального OFF-интервала выполни подробную диагностику.

Для каждого кадра сохранить:

- Оригинальное изображение с правильной ориентацией.
- Обнаруженные ArUco и их ID.
- Оценку гомографии.
- Результат перспективного преобразования.
- Маску достоверной регистрации.
- Общую область с опорным кадром.
- Разность до компенсации освещения.
- Разность после компенсации освещения.
- Тепловую карту остаточной разницы.
- Маску `residual > 40`.
- Долю изменённых пикселей.
- Число реально светящихся или подозрительно цветных областей.
- Причину принятия или отклонения.

Отдельно рассчитать:

- RMSE регистрации ArUco.
- Число использованных меток.
- Изменение масштаба и перспективы.
- Оценённые gain/offset освещения.
- Долю остаточных изменений внутри платы.
- Долю изменений возле контрастных элементов шелкографии.
- Долю изменений на границах маски.
- Наличие признаков motion blur.

Найти ответ на вопрос:

**Почему визуально выключенные кадры 13, 28 и 43 отклоняются как LIGHTING_OR_MOVING_OBJECT?**

Установить, что именно вызывает срабатывание:
- Движение телефона.
- Ошибка гомографии.
- Интерполяция при warpPerspective.
- Автоматическая экспозиция.
- Изменение освещения.
- Недостаточная устойчивость сравнения с первым кадром.
- Иная причина.

Не объявлять одну из этих гипотез доказанной без проверки.

## 5. Исправить Automatic OFF

Нужно сохранить главный принцип:

**OFF формируется автоматически из реальных кадров выключенной платы с независимой регистрацией ArUco.**

Предлагаю рассмотреть следующие улучшения.

### 5.1. Адаптивный отбор кадров

Сейчас недостаточно гибкая выборка нескольких кадров может привести к полному отказу, даже если внутри начального интервала есть десятки подходящих OFF-кадров.

Реализовать поиск дополнительных кандидатов внутри выбранного интервала при отклонении первых образцов.

Ограничить количество хранимых полноразмерных кадров и вычислительные затраты.

Выбирать качественные кадры, а не просто первые три подходящих по порядку.

### 5.2. Более устойчивая оценка изменений

Разделить:

- Глобальное изменение освещения.
- Геометрические остатки.
- Шум камеры и компрессии.
- Локальное цветное свечение.
- Перекрытие платы посторонним объектом.

Не считать небольшие остатки на белой шелкографии доказательством включения LED.

Рассмотреть:
- Робастные статистики различий.
- Исключение границ высококонтрастных объектов из оценки общего изменения.
- Локальные признаки цветности.
- Согласованность изменений между несколькими кадрами.
- Оценку остаточной геометрической ошибки.

Не отключать проверки реального свечения.

### 5.3. Эталон OFF из нескольких наблюдений

Сформировать устойчивую модель по нескольким независимо зарегистрированным кадрам.

Сохранить поканальную медиану или обоснованную альтернативу.

Учитывать маски доверия.

Не включать в OFF-эталон пиксели, для которых недостаточно достоверных наблюдений.

### 5.4. Защита от загрязнения фона

Построить отрицательные тесты:

- Светодиод включён на протяжении всего выбранного интервала.
- Светодиод включился посреди интервала.
- Имеется яркий цветной отражённый свет.
- Объект перекрывает часть платы.
- Метки ArUco потеряны.
- Сильный motion blur.
- Существенное изменение освещения.

В таких случаях алгоритм должен отказать или запросить другой интервал, если не может достоверно определить OFF.

Не использовать ожидаемые времена RED/GREEN/BLUE для принудительного принятия сомнительных кадров.

## 6. Контроль покрытия платы

Для полученной OFF-модели обязательно оценить:

- Общую долю валидных пикселей.
- Покрытие области PCB.
- Покрытие LED49.
- Покрытие известных LED.
- Области, непригодные для DISCOVER.

Недопустимо объявлять OFF успешным, если светодиоды находятся вне достоверной области анализа.

Показать карту покрытия в диагностическом отчёте.

Особенно проверить LED49, поскольку в ранней версии Vision этот светодиод исключался из общей маски.

## 8. Повторный Benchmark на настоящем MP4

После исправления Automatic OFF обязательно выполнить Benchmark на исходном файле `VID_20261117_101549.mp4`.

На ПК пользователя:

- Intel Core i9-9900K.
- 64 ГБ RAM.
- Python 3.12.3.
- OpenCV 4.14.0.

Вначале выполнить короткий тест на 120 кадрах.

Затем выполнить **полную обработку всех 922 кадров** оптимизированным гибридным вариантом.

Проверить отдельно:

- `KNOWN_LEDS`.
- `DISCOVER`.

Для каждого режима сохранить:
- Mean.
- P50.
- P95.
- P99.
- Max.
- Реальный throughput FPS.
- Decode time.
- ArUco detect time.
- Homography time.
- Warp time.
- LED detection time.
- RAM / CPU.
- Число зарегистрированных кадров.
- Число недостоверных кадров.
- Причины отказов регистрации.
- Время построения OFF.

Не считать 30 FPS доказанными, если получен только хороший средний FPS на коротком отрезке.

Указать, что реальное видеоустройство работало примерно на 29,92 FPS.

Проверить правильность поворота −90° и PTS после декодирования.

Если полная обработка слишком дорогая, выполнить полный гибридный прогон, а медленный полноразмерный вариант оставить на репрезентативном подмножестве. Чётко обозначить несопоставимые тесты.

## 9. Проверка реальных RGB-событий

Текущая версия ещё не обязана поддерживать полноценное автоматическое построение событий по всему видео.

Но в ходе анализа проверить, что на кадрах с заведомо видимым свечением:

- LED49 действительно обнаруживается.
- Цвет классифицируется как RED/GREEN/BLUE.
- Не появляются ложные известные LED.
- При потере достоверной геометрии результат не выдаётся как подтверждённый.

Для DISCOVER проверить, что светящийся LED49 возникает как оптический кандидат даже без предварительного знания его координаты.

Если текущий `VideoEngine` и `EventAggregator` позволяют сохранить предварительную временную последовательность событий, сделай это в отчёте.

Не заявлять, что реализован полный production-анализ видео, если проверка выполняется только на отдельных кадрах.
