# GS75_RGB_Research — v0.4.4: Short Pulse Experiment, единый рабочий процесс GUI и таблица электрических/оптических соответствий

Работаем в существующем репозитории:
https://github.com/AlexeyNV/GS75_RGB_Research

Текущая версия: RGB Vision v0.4.3, коммит cf00ccb.

## Цель

Пользователь хочет исследовать 40-контактный шлейф RGB-подсветки MSI GS75 полностью через GUI, без PowerShell и ручного ввода CDC-команд.

На текущем этапе необходимо:

1. Добавить безопасный эксперимент коротких импульсов LED49.
2. Упростить переход от аппаратного эксперимента к анализу записанного MP4.
3. Сделать временную шкалу обнаружений основным результатом анализа видео.
4. Сопоставлять электрические импульсы из журнала STM32 с независимыми оптическими событиями.
5. Реализовать экспорт единой таблицы электрических и оптических соответствий.
6. Подготовить архитектуру для последующего сканирования всех направленных комбинаций KP1–KP40.

Прошивку STM32 пока не менять.

## 2. Новый сценарий LED49_SHORT_PULSE_TEST

Добавить в существующей вкладке «Видеоэксперимент» выбор сценария.

Варианты:
- LED49 RGB 5 seconds — существующий сценарий.
- LED49 Short Pulse Test — новый сценарий.

Для Short Pulse Test предоставить настройки через GUI:

- Цвет: RED по умолчанию.
- Длительности: 100, 200, 300 мс.
- Повторы каждой длительности: 10.
- Пауза OFF между импульсами: 700 мс.
- Начальный OFF: 5000 мс.
- Завершающий OFF: 5000 мс.
- Режим последовательности: по длительностям или перемешанный с известным seed.
- Профиль анализа: Short Pulse / Experimental.

Предусмотреть опциональный синхронизационный маркер: однократное включение LED49 RED на 1000 мс с отдельной OFF-паузой 2000 мс перед серией коротких импульсов.

Маркер должен иметь собственную запись в журнале и не учитываться при расчёте качества обнаружения коротких импульсов.

Все действия запускать только после явного подтверждения пользователя.

Использовать существующую команду:

PHOTO LED49 RED duration_ms

Не использовать PAIR для этого первого эксперимента.

## 3. Безопасное аппаратное управление

Сохранить проверки FW 0.1.2:
- PING/INFO/STATUS.
- ADC VALID и свежесть измерений.
- SELFTEST.
- FAULT=NONE.
- DISARMED.
- SOURCE/SINK EN=0.
- Подтверждение U13 OPEN и R1=2700 Ом оператором.

Для каждого отдельного PHOTO:
- Выполнить ARM согласно существующей безопасной логике.
- Отправить PHOTO.
- Проверить ACK с правильными параметрами.
- Дождаться DONE с соответствующим ID.
- Проверить TIMEOUT, FAULT, ток, samples, elapsed.
- Подтвердить OFF и выключенные EN.
- Только затем переходить к следующему импульсу.

Каждый PHOTO должен быть отдельной ограниченной аппаратной операцией. Не допускать перекрытий.

Кнопка «Прервать / OFF» должна иметь приоритет над сценарием.

При FAULT, потере USB, неверном ADC, отсутствии DONE или неподтверждённом OFF немедленно прекращать серию. Не выполнять автоматического повторного запуска после аварии.

IWDG отсутствует. Отображать предупреждение о необходимости физически доступного отключения питания.

## 4. Удобный сценарий пользователя

Нужен последовательный рабочий интерфейс:

**Эксперимент → Видео → Анализ → Временная шкала → Экспорт.**

После завершения аппаратного эксперимента:

1. Кнопка «Добавить записанное видео».
2. Выбор MP4 в стандартном диалоге Windows.
3. Кнопка «Анализировать эксперимент».
4. Автоматическое открытие связанного проекта и калибровки.
5. Автоматическое построение OFF из начала видео.
6. Запуск режима DISCOVER или KNOWN_LEDS.
7. Автоматическое применение Short Pulse / Experimental.
8. Открытие временной шкалы.
9. Сопоставление оптических событий с журналом.
10. Экспорт результатов.

Не требовать от пользователя вручную выбирать пути к JSON при обычной работе.

Если привязка проекта или калибровки отсутствует, предложить выбор в GUI.

Не запускать «Измерение производительности» вместо анализа событий.

Раздел «Производительность видео» оставить отдельно как диагностический инструмент.

## 5. Временная шкала и просмотр результатов

Использовать существующее окно v0.4.3, улучшив удобство.

Обязательно показывать:
- Полную временную шкалу записи.
- Подтверждённые события.
- Кандидатов.
- Неопределённые интервалы.
- Состояние OFF.
- Цвета свечения.
- Положения найденных LED.
- Границы импульсов по PTS.

При выборе события:
- Переходить к соответствующему кадру MP4.
- Показывать ROI.
- Показывать ток, если найдена соответствующая электрическая операция.
- Показывать SOURCE/SINK.
- Показывать точность/неопределённость сопоставления.

Раздельно отображать данные STM32 и оптические результаты.

Не назначать электрическим фронтам точность по PTS видеокадров.

## 6. Проверка коротких импульсов

Для каждой заданной длительности считать:

- Количество запрошенных импульсов.
- Количество успешно завершённых аппаратных операций.
- Количество оптически обнаруженных событий.
- Количество CONFIRMED.
- Количество CANDIDATE.
- Количество MISSED.
- Количество UNOBSERVABLE из-за геометрии/экспозиции.
- Количество ложных обнаружений.
- Распределение ошибок временных границ.
- Уровень сигнала и уверенность.

Не считать отсутствие оптического события доказательством отсутствия света, если LED не был достоверно наблюдаем.

Проверить короткие импульсы на 30 FPS. Впоследствии обеспечить сопоставимость с 60 FPS.

Минимальную надёжную длительность определять по результатам серии, а не по единичному успешному импульсу.

## 7. Синхронизация USB и видео

Использовать существующие данные:
- session.json.
- ACK/DONE.
- Host monotonic timestamps.
- Video PTS.
- Оптические события.

Сначала независимо выполнить оптическое обнаружение, затем сопоставление с электрическим журналом.

Для смещения шкал использовать синхронизационный маркер и последовательность событий. Не полагаться на совпадение системных часов телефона и компьютера.

Проверять однозначность сопоставления.

При необходимости оценивать смещение и медленный дрейф времени, но не подгонять модель без достаточных опорных событий.

При неоднозначности возвращать AMBIGUOUS, а не автоматически связывать ближайшие интервалы.

Не заменять фактические PTS номинальными временами эксперимента.

## 8. Итоговая таблица

Разработать единый машиночитаемый формат:

`electrical_optical_mapping.csv`

- experiment_id
- operation_id
- source_kp
- sink_kp
- requested_duration_ms
- measured_duration_ms
- current_avg_ua
- current_max_ua
- fault
- electrical_status

- color
- optical_start_pts
- optical_end_pts
- optical_confidence
- roi_coverage
- alignment_confidence
- operator_confirmation
- mapping_status

Возможные mapping_status:
- VERIFIED
- OPTICAL_CANDIDATE
- ELECTRICAL_ONLY
- NO_OPTICAL_OBSERVATION
- AMBIGUOUS
- REJECTED
- FAILED_OPERATION

Не заполнять неизвестные значения искусственными нулями.

Одна электрическая операция может соответствовать нескольким оптическим позициям. Схема должна поддерживать связь один-ко-многим.

Для неизвестных LED использовать track_id, не присваивать PCB LED ID автоматически.

Отдельно предоставить:
- electrical_operations.csv
- optical_events.csv
- electrical_optical_mapping.csv
- short_pulse_summary.csv

Все таблицы создавать и открывать через интерфейс.
