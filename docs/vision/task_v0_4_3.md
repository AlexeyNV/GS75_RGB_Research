# GS75_RGB_Research — RGB Vision v0.4.3: временной анализ RGB и автоматическое формирование событий из видео

Ты — инженер-разработчик систем компьютерного зрения на Python/OpenCV/PySide6.

Работаем в существующем репозитории:
https://github.com/AlexeyNV/GS75_RGB_Research

Текущая версия — v0.4.2, коммит `8b10165`.

## Главная цель

Реализовать полноценный **офлайн-анализ всей видеозаписи**, который преобразует покадровые результаты RGB Vision в достоверные световые события.

Пользователь должен открыть существующее приложение через `Start_RGB_Vision.bat`, выбрать MP4 и нажать «Анализировать видео».

Программа самостоятельно:
1. Формирует OFF-модель из начального интервала.
2. Регистрирует ArUco на видеокадрах.
3. Обнаруживает изменения подсветки.
4. Анализирует последовательность наблюдений во времени.
5. Находит начала и окончания включений.
6. Определяет LED, цвет и длительность.
7. Подавляет кратковременные ложные кандидаты.
8. Сохраняет неопределённые интервалы.
9. Отображает события на временной шкале в GUI.
10. Экспортирует полный отчёт.

Не изменять прошивку STM32 и не управлять физическим стендом во время автоматических тестов.

## 3. Состояния наблюдения

Раздели покадровые состояния и итоговые события.

Покадровые состояния:

- ON — достоверно обнаружено свечение.
- OFF — достоверно установлено отсутствие свечения в наблюдаемой области.
- UNCERTAIN — визуальная информация противоречива.
- INVALID_GEOMETRY — достоверное геометрическое наблюдение невозможно.
- NO_COVERAGE — область LED не покрыта валидной OFF-моделью.

Не преобразовывать UNCERTAIN, INVALID_GEOMETRY и NO_COVERAGE автоматически в OFF.

Для каждого наблюдения сохранять:
- PTS.
- Номер кадра.
- LED ID, если известен.
- Положение в координатах платы.
- Цвет.
- Яркость.
- Хроматический сигнал.
- Качество регистрации.
- Покрытие ROI.
- Причины неоднозначности.
- Оценку уверенности.

Не уничтожать исходные покадровые данные при временной фильтрации.

## 4. Temporal Event Detector

Реализуй отдельный модуль временного анализа.

Он должен выполнять:

- Отслеживание цветового сигнала во времени.
- Гистерезис включения/выключения.
- Устойчивое подтверждение события.
- Подавление кратковременных оптических артефактов.
- Обработку отсутствующих наблюдений.
- Объединение частей одного события.
- Разделение соседних событий.
- Оценку временных границ и их неопределённости.

Рассмотри конечный автомат состояний:

`OFF → POSSIBLE_ON → ON → POSSIBLE_OFF → OFF`

Предусмотри дополнительное состояние UNKNOWN при потере наблюдаемости.

Не превращать его автоматически в ON или OFF.

Используй временные интервалы в секундах по PTS, а не только количество кадров. Это важно для VFR-видео.

При короткой потере геометрии допускается сохранение гипотезы о продолжающемся событии, но в отчёте должен оставаться разрыв достоверности.

Не склеивать события через подтверждённый OFF-интервал.

При продолжительной потере геометрии событие необходимо завершить или разделить с пометкой неопределённости согласно обоснованной политике.

## 5. Короткие импульсы

Будущий аппаратный сканер будет использовать ограниченные импульсы PAIR продолжительностью 10–300 мс.

Поэтому временной фильтр нельзя оптимизировать только для пятсекундных включений.

Проверить работу на:
- 33 мс.
- 67 мс.
- 100 мс.
- 200 мс.
- 300 мс.
- 1000 мс.
- 5000 мс.

Различать обнаружение импульса и подтверждение его длительности.

При 30 FPS очень короткий импульс может оказаться между экспозициями. В таких условиях допустим результат MISSED/UNCERTAIN, но нельзя заявлять гарантированное обнаружение.

Порог минимальной продолжительности, гистерезис и допустимый разрыв должны быть настраиваемыми.

Предусмотреть профили:
- Reliable / Long Pulse.
- Short Pulse / Experimental.

Ни один профиль не должен скрывать недостаточную наблюдаемость.

## 6. KNOWN_LEDS

В режиме известных LED:

- Использовать существующую карту калибровки.
- Анализировать временной ряд для каждого LED отдельно.
- Объединять ON-наблюдения в события.
- Проверять устойчивость цвета.
- Отделять изменение яркости от цветового перехода.
- Обрабатывать возможное изменение RED → GREEN → BLUE без промежуточного OFF.
- Не создавать ложное событие из кратковременных отражений.

Итоговая запись должна содержать:
- LED_ID.
- KEY_NAME, если известен.
- COLOR.
- START_PTS.
- END_PTS.
- DURATION_S.
- START_FRAME.
- END_FRAME.
- CONFIDENCE.
- STATUS.
- COVERAGE.
- UNCERTAINTY_FLAGS.

Временные границы представлять с учётом дискретности видеокадров и интервалов, в которых наблюдений нет.

Не выдавать субкадровую точность, которую нельзя подтвердить.

## 7. DISCOVER

В этом режиме координаты неизвестных LED не задаются заранее.

Нужно:
1. Обнаруживать цветные кандидаты в кадрах.
2. Преобразовывать их координаты в систему платы.
3. Сопоставлять кандидатов между соседними кадрами.
4. Формировать пространственно-временные треки.
5. Объединять повторяющиеся наблюдения одного источника.
6. Отбрасывать одиночные нестабильные отражения.
7. Присваивать трекам статусы CONFIRMED / CANDIDATE / UNCERTAIN по объективным критериям.
8. Предлагать подтверждённые оптические позиции для добавления в карту LED.

Проверять пространственную близость, геометрическую неопределённость и временную непрерывность.

Не считать все прежние 68 кандидатов ложными заранее: исследовать их координаты, яркость, продолжительность и цвет.

**Никогда не назначать PCB LED ID автоматически только по оптической близости или порядковому номеру кандидата.**

Пользователь должен вручную подтвердить соответствие шелкографии и найденного источника.

## 9. Производительность

Использовать оптимизированный гибрид v0.4.2.

На реальном ролике текущие измерения:

- KNOWN: 47,00 мс/кадр, около 21,26 FPS.
- DISCOVER: 77,87 мс/кадр, около 12,84 FPS.

Не требуется достижение 30 FPS в этой версии.

Главные требования:
- Обрабатывать все 922 кадра.
- Не пропускать кадры ради повышения скорости.
- Не строить заново OFF для каждого кадра.
- Не выполнять повторно дорогие операции только ради временного анализа.
- Сохранять PTS.
- Сохранять отзывчивость GUI.
- Поддерживать Cancel.
- Не хранить все полноразмерные изображения в RAM.

Временной агрегатор должен обрабатывать компактные результаты кадров.

Измерить его дополнительную стоимость отдельно от OpenCV.
