# GS75_RGB_Research — RGB Vision v0.4-perf: производительность видеоанализа и автоматический OFF

Работаем в существующем репозитории `GS75_RGB_Research`, последний завершённый этап — RGB Vision v0.3.

Цель: измерить реальное время обработки видеокадра на компьютере пользователя, реализовать прототип автоматического формирования OFF-фона из начала видео и определить, достижим ли потоковый анализ 30 FPS без потери качества распознавания.

**Не изменять прошивку STM32 и не переписывать полностью работающий RGB Vision v0.3.**

## 2. Инструмент измерения производительности

Реализуй встроенный профилировщик видеокадров.

Измеряй отдельно:

1. VIDEO_DECODE — чтение и декодирование кадра.
2. ARUCO_DETECT — обнаружение меток.
3. HOMOGRAPHY — оценка преобразования и проверки качества.
4. IMAGE_RECTIFICATION — перспективная коррекция.
5. BACKGROUND_COMPENSATION — коррекция различий освещения.
6. LED_DETECTION — поиск светящихся областей.
7. COLOR_CLASSIFICATION — определение RGB.
8. EVENT_AGGREGATION — объединение кадров в события.
9. FRAME_TOTAL — полный цикл обработки.

Использовать `time.perf_counter_ns()`.

Измерять по крайней мере:
- Среднее время.
- Медиану.
- P95.
- P99.
- Максимум.
- FPS обработки.
- Потребление RAM, если доступно.
- Количество потерянных или недостоверных кадров.
- Количество успешно зарегистрированных кадров.

Время сохранения диагностических PNG, обновления GUI и записи результатов учитывать отдельно.

Профилирование проводить после прогрева декодера и OpenCV, без включённого подробного вывода каждого кадра.

## 4. Автоматическое создание OFF

Начальный интервал видеозаписи содержит только выключенные светодиоды.

Алгоритм:

1. Открыть видео.
2. Выбрать стартовый интервал, по умолчанию 2 секунды.
3. Проанализировать качество кадров и доступность ArUco.
4. Для каждого пригодного кадра вычислить собственную гомографию.
5. Совместить выбранные кадры в системе координат платы.
6. Исключить кадры с недостоверной регистрацией, движущимися объектами и существенными изменениями освещения.
7. Проверить отсутствие устойчивых локальных признаков свечения.
8. Построить устойчивую модель OFF, например медианное изображение по валидным областям.
9. Сохранить маску достоверности OFF, чтобы не анализировать пиксели без достаточных наблюдений.

Не хранить всю видеозапись или десятки полноразмерных кадров без необходимости.

Если автоматическое построение OFF невозможно, GUI должен сообщить причину и предложить выбрать подходящий интервал вручную.

**OFF нельзя получать простым копированием первого кадра без ArUco-коррекции.**

На последующих участках гарантированного OFF предусмотреть возможность аккуратного обновления фона, но не обновлять его во время подтверждённого свечения.

## 5. Прототип анализа последовательных кадров

Используй существующую модель OFF.

Для каждого кадра:
- Декодировать изображение.
- Обнаружить ArUco.
- Вычислить новую гомографию.
- Проверить геометрическое качество.
- Привести данные к координатам платы.
- Сравнить с OFF.
- Найти новое свечение.
- Определить цвет.
- Сохранить время и признаки достоверности.

При потере ArUco не назначать неизвестным областям LED ID.

Для временных меток использовать PTS видео, если доступны; учесть переменную частоту кадров.

Кадры не пропускать в офлайн-режиме ради увеличения показателя FPS.

## 6. Сравнение вычислительных архитектур

Сравнить минимум три подхода.

### A. Existing Full Frame

Прямое применение существующего фотоанализа к последовательным кадрам.

Обязательно исключить повторную обработку неизменного OFF при каждом кадре, но также измерить неизменённый baseline алгоритма для честного сравнения.

### B. Cached OFF + Full Frame

Один раз зарегистрировать OFF, затем для каждого кадра выполнять новую геометрию и полный анализ свечения.

Не генерировать диагностические копии всех полноразмерных изображений в рабочем цикле.

### C. Optimized Hybrid

Попробовать:
- Уменьшенное изображение для поиска ArUco, если метки остаются распознаваемыми.
- Расчёт гомографии по координатам исходного изображения.
- Грубый поиск светящихся областей на уменьшенной версии платы.
- Высокоразрешённый анализ только локальных кандидатов.
- Отдельный быстрый путь для KNOWN_LEDS.
- Переиспользование подготовленной OFF-модели.
- Сокращение больших временных массивов и копирований изображений.

При поиске ArUco на уменьшенном кадре обязательно проверить, что точность регистрации и доля потерянных меток не ухудшились недопустимо.

Оптимизация не должна превращать недостоверные результаты в уверенные обнаружения.

## 7. Воспроизводимые испытания

Проверить реальные фотографии LED49 OFF/RED/GREEN/BLUE как регрессионные данные.

Для видео использовать:
- Имеющееся пользовательское MP4, если оно доступно.
- Синтетическое видео с последовательностью OFF → RED → OFF → GREEN → OFF → BLUE → OFF.
- Синтетические движения камеры: сдвиг, поворот, наклон, изменение масштаба.
- Разные размеры кадров: 1080p, 1440p и 4K, если позволяют исходники и компьютер.

Не выдавать показатели синтетического теста за измерение на реальном телефоне.

Пройти тесты с полным отключением отладной визуализации и отдельно с открытым GUI.

Не подменять скорость обработки декодированием одних и тех же заранее загруженных кадров.

Разделить FPS декодирования, FPS обработки и сквозной FPS.

## 8. Критерии принятия решения

Для каждого варианта составить таблицу:

| Вариант | Mean ms | P95 ms | FPS | Peak RAM | Quality |
|---|---|---|---|---|---|

При оценке потокового режима ориентироваться на:

- 30 FPS: бюджет 33.3 мс на кадр.
- Для устойчивой обработки желательно среднее не более 25 мс, с контролем P95 и очереди кадров.
- При превышении бюджета определить узкое место.
- При недостижимых 30 FPS показать доступную устойчивую скорость.
- Для офлайн-анализа допускается обработка медленнее реального времени без пропуска кадров.

Не утверждать, что система способна работать в реальном времени, только на основании среднего FPS на коротком синтетическом ролике.
